# 第二大脑资产维护规则的提炼目标

本文记录本项目的目标：把第二大脑创建工具中的资产维护规则提炼为显式、可校验的规格，而不是继续依赖 `SKILL.md` 的自然语言描述做模糊判断。

---

## 记录对象

记录对象是 `BlackCat205/quanttide-profile-of-agent-engineering` 及其 `second-brain-ui-0.9.3-cross-platform` 分支上的第二大脑创建工具。选择该分支作为观察样本，是因为它同时包含规则的三种载体，且规模已在 [分支增量对比文档](../library/second-brain-ui-0.9.3-cross-platform-vs-main.md) 中实测。

## 规则现状与问题

工具中的资产维护规则目前散落在三处。`skills/second-brain-init/SKILL.md` 共 30 行，用自然语言描述执行步骤与完成判断，其中「领域边界是否准确、英文含义是否恰当」一类要求只写明「由人和 AI 审阅」，没有判定标准。`references/contract-rules.md` 共 71 行，以散文形式规定双轴命名、目录坐标、文档与许可、Git 与安全约束。`assets/specification.yaml` 与 `scripts/engine.py` 则是可执行部分：规格文件登记 20 类资产、17 个保留简称、20 个标准目录坐标，并把来源锁定到原始流程提交 `2b5666c` 与资产章程提交 `0301294`；执行器内含 `slug`、`safe_path`、`validate_config`、`validate_asset_contract`、`markdown_errors`、`domain_quality_warnings` 六个校验函数。

问题在于能程序判定的部分虽然存在，却与大量只能靠解读的描述混写在一起。AI 读到 `SKILL.md` 后自行理解并套用规则，规则冲突、条款缺省或边界模糊时没有统一裁决依据，同一输入在不同轮次可能得到不同结论；而程序已经能判定的部分，也没有一处集中的清单说明「哪些规则由程序管、哪些必须人来看」。

## 提炼目标

目标是形成一份显式的规则规格，使每条资产维护规则都具备三要素：明确的来源（章程条款或锁定的流程提交）、明确的判定方式（程序校验或人工审阅）、失败时明确的提示文本。判断目标是否达成可以用一句话衡量：在没有 AI 参与的情况下，程序对同一输入给出的通过与否结论，与有 AI 参与时一致；AI 既不能放宽规则，也不能临时补写规则。

## 提炼范围

1. 命名规则：双轴与交点命名、20 类资产的仓库名模式、17 个保留简称，以及字符格式与长度限制；
2. 目录坐标：`apps`、`packages`、`examples` 加 17 类 `data` 与 `docs` 坐标，共 20 个标准位置；
3. 文档与许可：领域 README 的必备章节、`CHANGELOG` 的结构要求、新仓库 CC BY 4.0 与聚合容器 Apache 2.0 的先例；
4. Git 与安全：只暂存本任务路径、按子仓库到根仓库的顺序提交、创建与推送必须绑定计划编号的人工确认；
5. 契约一致性：`.quanttide/asset/contract.yaml` 的路径与仓库地址同 `.gitmodules` 逐项一致，并可由资产云 CLI 复验。

## 与 SKILL 的分工

`SKILL.md` 保留它擅长的部分：理解用户意图、调查已有先例、选择场景、把意图写成规格允许的配置。规则正文移出 `SKILL`，进入锁定来源的规格文件，由执行器统一校验。仍然只能由人判断的内容，例如领域边界是否合理、英文全名含义是否准确，在规格中显式标注为人工审阅项，与程序校验项分列呈现，两者之间不留「AI 自行把握」的中间地带。

## 下一步

按上节范围逐条列出规则清单，为每条补上来源与判定方式。判定方式缺失的规则先补定义再进规格，不把含糊条款直接搬进规格文件继续含糊。
